# AI Gateway Architecture Patterns and Design Analysis

## 1. Body-Aware Proxy Architecture: A Structural Departure

Traditional reverse proxies operate at the header level. Routing decisions are made on URL path, Host header, and TLS SNI. Rate limiting counts requests. Authentication checks bearer tokens. The response flows back untouched. This model has worked for two decades because HTTP workloads are opaque payloads bracketed by metadata -- the proxy has no business reading the body.

AI traffic breaks this assumption at every stage. The request body carries the prompt, which determines cost (token count), routing target (model selection), security posture (PII content), and policy applicability (tenant identity embedded in conversation context). The response body determines compliance (generated content must pass guardrails), caching eligibility (semantic similarity, not URL identity), and billing (output token count is unknowable until the response completes). This bidirectional content dependency is what makes AI gateways architecturally distinct from API gateways that bolted on AI features.

Three proxy architecture patterns have emerged for handling body-aware workloads:

**Filter-pipeline (in-process).** The proxy loads a chain of filters that inspect and mutate both request and response bodies inline. Envoy's HTTP filter chain, NGINX's processor pipeline, and Pingora's `ProxyHttp` trait callbacks all follow this model. The advantage is latency -- no serialization boundary between filters. The cost is coupling: every filter runs in the proxy's address space, and a crash in a guardrails filter takes down the proxy. For AI workloads, the pipeline must buffer complete request bodies before routing (model selection requires the full prompt), which conflicts with streaming-optimized proxy architectures.

**External processor (ext_proc).** Envoy's ext_proc filter forwards request/response phases to an external gRPC service, which can inspect headers, body chunks, and trailers, then return mutations. Envoy AI Gateway v1.0 uses this pattern: the AI Gateway External Processor runs as a separate service, receiving forwarded traffic from Envoy's filter chain for AI-specific logic -- token counting, provider translation, credential injection. The ext_proc stream is per-request (not shared across requests), preserving isolation. Body send modes (BUFFERED, STREAMED, FULL_DUPLEX_STREAMED) give fine-grained control over how much body content crosses the gRPC boundary. The trade-off is latency from serialization and the gRPC hop, plus the 8KB default buffer limit that requires careful configuration for large prompts.

**Sidecar / per-node proxy.** Istio ambient mesh's ztunnel demonstrates a different decomposition: a per-node Rust proxy handles L4 concerns (mTLS, L4 auth, telemetry) while per-namespace Envoy waypoint proxies handle L7. This two-tier model moves policy enforcement closer to the workload without per-pod overhead. For AI workloads, the pattern is less directly applicable because body-aware processing inherently requires L7 inspection, but the decomposition principle -- separate what can run at L4 from what requires L7 -- influences how front-door vs. AI data-plane responsibilities are divided.

**Where Praxis sits.** Praxis implements the filter-pipeline pattern natively in Rust on Pingora's `ProxyHttp` trait, with the critical difference that its filters are purpose-built for AI workloads from the start rather than adapted from general-purpose HTTP filters. The filter ordering (identity, model resolution, entitlements/quotas/budget, API translation, guardrails, credential injection, routing) is a fixed, AI-native pipeline. For the 3.6 transitional architecture, Praxis attaches via ext_proc over OSSM 3.4 (Envoy 1.38), accepting the serialization cost for compatibility. The long-term path replaces Envoy entirely for AI traffic, eliminating the ext_proc hop and the composability problems it creates.

### The Composability Problem

When multiple components independently make routing decisions -- gateway, model router, inference scheduler -- each becomes a "routing authority" that can override or contradict the others. Envoy Gateway's policy model illustrates the challenge: only one SecurityPolicy can target a single Gateway API resource, and Kuadrant's Defaults and Overrides mechanism (from GEP-713) exists precisely to prevent lower-level policies from bypassing higher-level constraints. In AI gateway deployments, the problem compounds because model routing, token budget enforcement, and placement decisions are often made by different systems (OGX, ITS, EPP) that have no shared policy plane.

Praxis's architectural response -- one router, one policy plane, one configuration authority -- directly addresses this. Every request traverses a single filter pipeline with a deterministic ordering. There is no second routing decision downstream that could contradict the policy decisions made upstream. This is architecturally novel compared to the Envoy AI Gateway's two-component data plane (Envoy Proxy + External Processor) or the multi-layer policy composition that Kuadrant manages through its policy-machinery library.

## 2. The Rust Proxy Ecosystem

The shift toward Rust for infrastructure proxies accelerated through 2025-2026, driven by memory safety requirements and performance parity with C/C++. Five projects define the current landscape:

**Pingora (Cloudflare).** The foundation. Pingora serves over 1 trillion requests/day at Cloudflare, consuming 70% less CPU and 67% less memory than the NGINX deployment it replaced. Its `ProxyHttp` trait provides filter and callback hooks for customizing request processing, and its two-stage connection pool with lock-free hot pool enables efficient connection reuse across threads. Pingora v0.7.0 (2026) has evolved into a "Programmable Network Infrastructure" framework. As of May 2026, it also powers Cloudflare's cache layer. For AI gateway use cases, Pingora's strengths are its programmability (the proxy becomes software, not configuration), its async runtime on tokio, and its proven scale. Its weakness is that it is a framework, not a product -- building an AI-aware proxy on Pingora requires implementing all the AI-specific logic. This is exactly what Praxis does: it uses Pingora as the proxy core and builds the AI data-plane logic on top.

**River (ISRG/Prossimo).** Built on Pingora by the Internet Security Research Group (the organization behind Let's Encrypt), River aims to be a memory-safe drop-in replacement for NGINX in reverse proxy deployments. Currently at v0.5.0 and in early developer preview, River adds WASM-based scriptability for plugin extensibility. River validates Pingora as a viable foundation for production reverse proxies but targets traditional HTTP workloads rather than AI-specific use cases. It does not address body-aware processing, model routing, or token-based rate limiting.

**Ztunnel (Istio).** Purpose-built for Istio ambient mesh, ztunnel handles L3/L4 concerns (mTLS, authentication, L4 authorization, telemetry) as a per-node proxy written in Rust. A 2025 Trail of Bits security audit found zero code vulnerabilities. Performance benchmarks show higher TCP throughput than even in-kernel data planes like IPsec and WireGuard, with 90%+ reduction in per-workload proxy memory versus Envoy sidecars. Ztunnel's relevance to AI gateways is architectural rather than functional: it demonstrates how to decompose proxy responsibilities by layer (L4 at the node, L7 at the waypoint), a pattern that maps to Praxis's three-layer model where the front door handles TLS termination and admission while the AI data plane handles body-aware processing.

**Linkerd2-proxy.** A per-pod micro-proxy for the Linkerd service mesh, using roughly 20-30 MB per sidecar versus 50 MB+ for Envoy. Linkerd 2.19 (October 2025) shipped post-quantum cryptography via ML-KEM-768 for mTLS tunnels. In 2025 benchmarks, Linkerd led at every load level: 11.2ms ahead of ambient Istio at p99 under 2000 RPS. Linkerd2-proxy's per-pod deployment model and tight resource envelope are relevant if AI workloads need per-pod policy enforcement, but its L7 feature set is focused on service mesh concerns (retries, timeouts, observability) rather than AI-specific processing.

**Orion (KMesh).** A Rust-based proxy under the KMesh project (Huawei-originated, CNCF-aligned), attempting to be a drop-in replacement for Envoy Proxy. Orion integrates with KMesh's eBPF-based kernel-native traffic governance, which reduces forwarding latency by over 60% compared to userspace proxies by sinking L4 and simple L7 traffic governance into the kernel. Orion is passing basic Kubernetes Gateway API conformance tests. The KMesh + Orion combination is architecturally interesting for AI gateways because it demonstrates how eBPF can accelerate the non-AI portions of the traffic path (L4 routing, mTLS acceleration) while a Rust proxy handles the L7 body-aware processing that requires userspace logic.

**Praxis's position.** Praxis builds on Pingora (the most proven foundation), targets AI workloads specifically (unlike River), operates at L7 with full body awareness (unlike ztunnel), and owns the complete AI policy pipeline (unlike Orion, which delegates policy to KMesh's kernel layer). The closest architectural analog is Envoy AI Gateway, but Praxis replaces the C++ proxy core with Rust and eliminates the ext_proc boundary by implementing AI logic directly in the filter pipeline.

## 3. Agentic Loop Orchestration Inside Gateways

Traditional proxy request lifecycles are stateless: request arrives, filters execute, upstream responds, response filters execute, client receives response. The entire interaction is bounded by a single HTTP transaction. Agentic AI workloads break this model fundamentally.

An agentic loop -- as implemented by OpenAI's Responses API or equivalent server-side orchestration -- involves multiple inference rounds within a single logical request. The model generates a response that includes tool calls; the system executes those tools; the results are fed back to the model; the model generates another response; this repeats until the model produces a final answer or a budget is exhausted. Each iteration is a separate inference call, but they are all part of one conversation session with shared state.

When a gateway owns this loop (as Praxis does for the Responses API), the proxy request lifecycle transforms:

**Re-entrant request handling.** Each inference round within the loop is a new upstream request, but the gateway must maintain session context across rounds. This is not connection pooling or keep-alive -- it is semantic state (conversation history, accumulated token count, tool execution results) that must persist across what are logically separate HTTP transactions. OpenAI's server-side solution uses `previous_response_id` chaining and, since February 2026, a durable Conversations API that stores items with no 30-day TTL. Praxis must implement equivalent state management for self-hosted models that lack server-side conversation storage.

**Fan-out/fan-in for inference-time scaling.** When a model request triggers multiple tool calls, the gateway must fan out to execute them (potentially in parallel), collect results, and fan back into the next inference round. This resembles the Parallel Fan-Out orchestration pattern identified in the agent orchestration literature, but it happens inside the proxy's filter pipeline rather than in an external orchestration framework. The implication is that the proxy must manage concurrent upstream connections within a single logical request -- a capability that traditional proxy architectures do not support.

**Auto-compaction and context management.** Long-running agentic sessions accumulate conversation history that can exceed model context windows. OpenAI's solution (released February 2026) is server-side compaction: when the rendered token count crosses a configurable threshold, the server triggers a compaction pass that produces an encrypted, token-efficient summary of prior context. The compacted output includes an opaque blob that the server rehydrates on subsequent requests. For a gateway implementing this pattern with open-weight models, the compaction logic must be part of the filter pipeline -- triggered between inference rounds, not as a separate API call. This is a novel requirement: the proxy is not just forwarding requests but actively managing the content it forwards.

**Budget enforcement across loops.** A single agentic request can generate 15+ inference calls (the literature documents 5-agent workflows with 3 model calls per step). Token costs compound multiplicatively. Per-request rate limiting is meaningless; the gateway needs per-session budget tracking that spans the entire loop. In Praxis's architecture, every loop iteration and tool call traverses the full policy pipeline, which means the entitlements/quotas/budget filter sees every inference round and can enforce cumulative limits. This is architecturally cleaner than frameworks where budget enforcement sits outside the inference loop and can only observe aggregate consumption after the fact.

**Where this differs from traditional orchestration.** The agentic orchestration literature (LangGraph, OpenAI Agents SDK, Google ADK) places loop management in application-layer frameworks. The emerging consensus in mid-2026 is that "the orchestration layer should focus on routing, state management, and environment execution" while "the agent's cognitive loop is handled by the model." Praxis pushes this further: the routing, state management, and environment execution happen inside the proxy itself, making the gateway the orchestration layer rather than requiring a separate orchestration service between the gateway and the model.

## 4. Multi-Tenant Policy Composition

AI workloads introduce policy dimensions that traditional proxy policy models were not designed for. The shift from request-count rate limiting to token-budget governance, the need for hierarchical spend attribution across organizations/teams/users, and the variable cost of individual requests (a single LLM call can range from hundreds to millions of tokens) all require new policy primitives.

**Tenant identity as a pipeline primitive.** In Praxis's filter pipeline, identity resolution is the first filter. This is deliberate: every subsequent filter (model resolution, entitlements, quotas, budget, guardrails) depends on knowing who is making the request. In Envoy's model, identity is established by authentication filters (JWT, mTLS) but is not inherently linked to downstream policy decisions -- the connection between "who you are" and "what budget applies" requires explicit configuration across separate policy resources (SecurityPolicy, RateLimitPolicy, BackendTrafficPolicy). Praxis collapses this into a single pipeline where identity propagates automatically through every filter stage.

**Session-scoped budgets.** Traditional rate limiting operates on fixed time windows (requests per minute). AI workloads need session-scoped budgets that span multiple requests within an agentic loop and account for variable token consumption. The emerging pattern (documented in LiteLLM's hierarchical model and Bifrost's four-tier system) is pre-dispatch budget enforcement: estimate token cost before sending to inference, reserve against the budget, execute, then reconcile actual usage. For cross-datacenter deployments, strict consistency adds 1-5ms latency per request; the pragmatic approach is eventual consistency with split budgets -- each datacenter gets an allocated share, with periodic reconciliation. Redis Cluster in AP mode with Lua-scripted atomic operations is the common production implementation.

**The "one authority per layer" principle.** Envoy Gateway enforces that only one policy of a given type can target a single resource -- you cannot attach two SecurityPolicies to the same Gateway. Kuadrant extends this with merge strategies (atomic defaults, atomic overrides) that determine how policies at different hierarchy levels compose. The rationale is bypass prevention: without this constraint, a route-level policy could inadvertently override a gateway-level security requirement. Praxis's single-pipeline model enforces this principle structurally rather than through CRD validation -- there is only one place where each policy decision is made, and the pipeline ordering determines precedence.

**Comparison with Envoy's policy model.** Envoy AI Gateway v1.0 provides token-based rate limiting, BackendSecurityPolicy for credential management, and provider-specific protocol translation. But these operate through Envoy's general-purpose policy attachment mechanism, which means they compose with other Envoy policies (SecurityPolicy, ClientTrafficPolicy) through the Gateway API hierarchy. This is powerful for integration with existing infrastructure but creates the composition complexity that Kuadrant's policy-machinery library exists to manage. Praxis trades this flexibility for simplicity: the AI policy pipeline is self-contained, and integration with non-AI infrastructure happens at the front-door layer rather than through shared policy composition.

## 5. Three-Layer Architecture Analysis

The three-layer model decomposes AI gateway functionality into distinct responsibility boundaries:

**Layer 1: Front Door (TLS termination, admission).** Handles TLS termination, client authentication, basic admission control, and general-purpose HTTP processing. In the 3.6 transitional architecture, this is OSSM 3.4 (Envoy 1.38). The front door is intentionally AI-unaware -- it applies the same security and admission policies to AI traffic as to any other HTTP traffic. This layer benefits from mature, battle-tested proxy implementations and should not require AI-specific modifications.

**Layer 2: AI Data Plane (filter pipeline, routing authority).** The body-aware processing layer where AI-specific logic lives: model resolution, token counting, budget enforcement, API translation across providers, guardrails, and intelligent routing. In Praxis, this is the filter pipeline running on Pingora. The key architectural decision is that this layer is the single routing authority for AI traffic -- it determines which model instance receives the request based on policy, budget, and model capabilities. Having a single routing authority here prevents the policy bypass problems that arise when multiple systems independently make routing decisions.

**Layer 3: Placement (KV-cache-aware scheduling).** The infrastructure layer that selects the specific model replica based on runtime state: KV cache locality, GPU utilization, queue depth, and LoRA adapter availability. This is the domain of llm-d's Endpoint Picker (EPP), which maintains a near-real-time index of KV cache block locality across all vLLM pods. The EPP demonstrates why placement must be cache-aware: round-robin load balancing is actively harmful for LLM inference because it discards computed KV cache state. Validated benchmarks show 57x faster time-to-first-token (TTFT) and 2x throughput versus round-robin on 8 pods with 16 H100 GPUs. The EPP also balances cache affinity against load -- without load-awareness, prefix-only routing succeeded on only ~55% of requests at high QPS; with combined scoring, 100% success rate and 5x lower inter-token latency.

**Separation of concerns vs. single-binary.** The three-layer model creates clear API boundaries: Layer 2 tells Layer 3 "route this request to model X," and Layer 3 handles the placement decision. This separation allows independent evolution (Praxis can add new filters without changing llm-d, and llm-d can add new placement strategies without changing Praxis) and independent scaling (the AI data plane scales with request volume while the placement layer scales with model replica count). The alternative -- a single binary that handles both policy and placement -- reduces operational complexity but couples concerns that evolve at different rates and are maintained by different teams.

**The ext_proc attachment as transitional architecture.** In 3.6, Praxis attaches to Envoy via ext_proc, creating a two-hop data path (client to Envoy to Praxis via gRPC to upstream). This is explicitly transitional: it allows Praxis to be deployed alongside existing OSSM infrastructure without requiring customers to replace their service mesh. The cost is the serialization overhead of the ext_proc gRPC stream (particularly for large request bodies) and the loss of direct control over TLS termination and connection management. The long-term architecture replaces Envoy entirely for AI traffic, with Istio deploying Praxis as the gateway data-plane image -- eliminating the ext_proc hop while preserving the three-layer separation between Praxis (Layers 1+2) and llm-d EPP (Layer 3).

## Open Questions

**Plugin ordering across contexts.** When the agentic loop microservice integrates with the filter pipeline, different plugin orderings may be appropriate for outer-gateway requests (where identity resolution and admission are primary) versus inner-loop iterations (where budget tracking and tool authorization are primary). Whether this requires a configurable pipeline or separate pipeline instances per context is an open design question. The Envoy ext_proc model handles this by allowing the external processor to change processing mode on a per-message basis, but Praxis's native pipeline would need its own mechanism.

**Conversation state for self-hosted models.** OpenAI's Conversations API and server-side compaction solve state management for their hosted models, but self-hosted vLLM deployments lack equivalent server-side state. The gateway must either implement its own compaction (becoming a stateful service with storage requirements) or rely on client-side context management (pushing complexity to application developers). The choice has significant implications for the agentic loop: if the gateway owns the loop, it must also own the state.

**Cross-datacenter rate limit enforcement.** The literature converges on eventual consistency with split budgets as the pragmatic approach, but the specific split algorithm matters. Static allocation wastes capacity when traffic is asymmetric; dynamic reallocation requires a coordination protocol that itself has latency. For AI workloads where a single request can consume a significant fraction of a tenant's budget, the reconciliation window must be short enough to prevent meaningful oversubscription. Redis Cluster in AP mode with Lua-scripted atomic operations is the current standard, but whether this scales to the token-level granularity that AI budgets require at cross-datacenter distances remains to be validated in production.
