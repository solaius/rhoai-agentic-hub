CFP Abstract

Every enterprise can get an agent running in a notebook. Making it production-ready — with execution isolation, cryptographic identity, policy enforcement, and a complete audit trail — is where 88% of pilots fail. Meanwhile, agents in the wild face a 78.3% attack success rate in controlled testing.

In this session, we start with an ungoverned agent prototype and walk through Red Hat AI's three-layer security and governance model, step by step with live demos and an attack-and-defend scenario:

Layer 1: OpenShell Sandbox Isolation — Deploy the agent into an OpenShell sandbox (co-engineered with NVIDIA) with kernel namespaces, seccomp profiles, and capability dropping. We trigger a malicious tool call and show sandbox containment in action — then compare the architecture to gVisor and Kata Containers to explain the design tradeoffs.

Layer 2: SPIFFE/SPIRE Cryptographic Identity — Assign the agent a SPIFFE identity via SPIRE: verifiable, short-lived SVIDs that federate across clusters. No more shared service accounts. We walk through the identity chain and why NIST and IETF AIMS are converging on SPIFFE as the standard for non-human identity.

Layer 3: AI Gateway Policy Enforcement — Route the agent's LLM calls through AI Gateway with OPA policies enforcing token budgets, sensitive data filtering, and tool call restrictions. Every interaction is logged with full identity context.

The session culminates in a live attack-and-defend scenario demonstrating all three layers working together, producing a complete audit trail. You leave with an architecture pattern you can whiteboard with any customer stuck between "it works in dev" and "my CISO won't sign off."

CAI: Demo support Live attack-and-defend demo: deploy agent, trigger malicious tool call, show sandbox containment, SPIFFE identity chain, Gateway policy + audit trail. Before/after contrast is the dramatic arc.
Merges the governance journey and security deep dive into one comprehensive session. The prototype-to-production arc gives it narrative structure; the attack-and-defend demo and gVisor/Kata comparison give it technical credibility. Critical for FSI (14 accounts), defense (3 accounts). NVIDIA co-engineering adds enterprise weight. Natural co-speaker: SA or specialist in security-sensitive verticals.

CFP Abstract

Gartner published its inaugural Market Guide for Guardian Agents in 2026, predicting that by 2028 every enterprise will need a governed agent inventory. Today, 82% of enterprises have discovered agents running that nobody deployed. Most organizations can't answer a basic question: how many agents are running in my environment?

This session goes deep on the technical architecture of Red Hat AI's Agent Registry — the only self-managed, disconnected-capable, governed fleet registry with lineage tracking:

OCI Packaging — Agents packaged as OCI artifacts with immutable digests, signed provenance, and declarative dependency manifests. We walk through the packaging format and explain why OCI (not custom APIs) is the right distribution mechanism for agent workloads.

Dependency Immutability — Pin agent dependencies (models, tools, guardrails) at deploy time with cryptographic verification. When a model is updated or a tool is patched, the registry tracks lineage and can enforce upgrade policies across the fleet.

Cross-Cluster Discovery — Federated agent discovery across multiple OpenShift clusters, air-gapped environments, and hybrid deployments. Agents registered in one cluster become discoverable (with policy controls) in another.

Fleet Lifecycle — Version management, rollback, canary deployments, and decommissioning with audit trails.

You leave understanding how to architect a governed agent inventory that scales from a single cluster to a global fleet.

Hyperscaler registries are cloud-locked; Red Hat's is open and self-managed. Co-speaker: an SA or consultant working in a regulated vertical.

CFP Abstract

A single user request can trigger a chain of agent calls — an orchestrator dispatching to specialist agents, each making multiple tool calls through MCP servers, routing through an AI Gateway, and consuming inference tokens across different models. When something goes wrong (and it will), how do you trace the failure back to its root cause?

This session covers the observability architecture for agentic workloads on Red Hat AI:

Distributed Tracing — OpenTelemetry-based tracing across multi-agent workflows. We walk through a trace that spans an orchestrator agent, two specialist agents, four MCP tool calls, and an AI Gateway policy decision — showing how each component contributes spans with semantic conventions for AI operations.

Debugging Silent Failures — When an MCP tool call fails and the agent hallucinates a response instead of reporting the error, how do you catch it? We show the telemetry patterns that reveal these failures and the alerting rules that surface them before they reach users.

Audit Log Architecture — Every LLM call, tool invocation, policy decision, and identity verification produces an audit event. We cover the log schema, retention policies, and how to query the audit trail for compliance reporting.

Cost Attribution — Token consumption tracking per agent, per workflow, per team. When your inference bill spikes, you know which agent workflow caused it.

You leave with observability patterns you can implement on day one of any agentic deployment.
